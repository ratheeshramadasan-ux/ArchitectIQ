ArchitectIQ — Enterprise UI Navigation & Functional Catalogue
Scope: Enterprise AI, Agentic AI, Automation, Document Intelligence, Workflow Orchestration, Governance, Operations, and Platform Administration.

For the parallel UI design work, I recommend defining ArchitectIQ as a multi-tenant enterprise platform with role-aware navigation, rather than a collection of independent screens.

The catalogue below is a proposed target-state design, combining our previously established ArchitectIQ requirements with additional enterprise capabilities. It is not a claim that all these features are already implemented.

20.3 Role Designer — M3.2 target design
The role designer needs resource-level, action-level and scope-level controls.
Custom Role Designer
Design concept

Role identityName, description, owner, status, version



Role scopeTenant / Organization / Folder / Project / Environment



Permission matrixResources × allowed actions



Conditional policiesABAC attributes, environment, risk, approval





Illustrative permission matrix
Resource	View	Create	Edit	Execute	Approve
Workflows					
Agents					
Test cases					
Deployments					
Role grants					

Illustrative Designer role only. Actual permissions must come from the authorization service.
Important authorization rules: System roles remain immutable. Only authorized Tenant Admins and Organization Admins may create, clone or customize custom roles within their permitted scopes. Role creation and role assignment are separate permissions. An administrator must not grant permissions beyond their own delegable authority. High-risk grants require appropriate approval, and backend authorization remains authoritative regardless of UI visibility.

10. Design decisions to standardize now
For ArchitectIQ, I recommend the following baseline:
Design concern	Proposed standard
Icon library	Lucide React, consistent 20px navigation icons
Main sidebar	Collapsible, grouped, searchable
Default navigation	8–12 top-level visible entries per role, remaining entries in grouped sections
Sidebar width	Approximately 256px expanded; 64–72px collapsed
Secondary navigation	Contextual tree or submenu within selected module
Object screens	Overview, configuration, activity, access and history tabs where applicable
Data grids	Shared reusable enterprise grid component
Designers	Shared canvas foundation with module-specific nodes
Task interactions	Unified task detail and action framework
Approvals	Reusable approval component with decision evidence
Role enforcement	Backend authorization with frontend permission-aware presentation
Theme	Light, dark, enterprise high-contrast
Accessibility	Keyboard navigation, focus indicators, WCAG 2.2 AA target
Design tokens	Shared colours, typography, spacing, radius and status tokens
Routing	Stable module and resource routes with scoped IDs
Navigation catalogue	Central typed registry with icon, route, feature flag and required permission

Architectural recommendation: Maintain the entire navigation and feature catalogue in a centralized UI Feature Registry, rather than hardcoding menus in separate React components. Each entry should define its module, parent, route, icon, resource type, required permission, feature flag, and contextual actions.

That will allow the UI team to build the full ArchitectIQ concept in parallel while the backend team completes M3.1 security hardening and M3.2 RBAC, without repeatedly redesigning the menu structure.

The next logical UI deliverable is a screen-by-screen specification and navigation registry based on this catalogue, with each page assigned a unique screen ID, route, component type, required permissions, and detailed actions.
